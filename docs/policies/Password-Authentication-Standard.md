| รายการ | รายละเอียด |
|--------|------------|
| **รหัสเอกสาร** | STD-ITSEC-001 |
| **เวอร์ชัน** | 1.0 |

## 1. วัตถุประสงค์

มาตรฐานฉบับนี้กำหนดข้อกำหนดขั้นต่ำสำหรับการจัดการรหัสผ่าน การพิสูจน์ตัวตน และการบริหารจัดการข้อมูลรับรอง (credentials) เพื่อ

1. ลดความเสี่ยงจากการเดารหัสผ่าน การขโมยบัญชี และการโจมตีแบบ credential stuffing / password spraying
2. ให้ระบบสำคัญมีการพิสูจน์ตัวตนหลายปัจจัย (MFA) ที่เหมาะสมกับระดับความเสี่ยง
3. ให้ผู้ใช้งานและผู้ดูแลระบบมีแนวปฏิบัติที่ชัดเจนและตรวจสอบได้
4. สนับสนุนการปฏิบัติตาม POL-ITSEC-001, พ.ร.บ.คุ้มครองข้อมูลส่วนบุคคล พ.ศ. 2562 และหลักการ ISO/IEC 27001/27002

---

## 2. ขอบเขต

มาตรฐานนี้ใช้กับ

- บัญชีผู้ใช้งานทุกประเภทขององค์กร (พนักงาน ผู้รับจ้าง พันธมิตร บัญชีบริการ)
- ระบบที่องค์กรเป็นเจ้าของหรือควบคุม รวมถึงอีเมล VPN คลาวด์ แอปพลิเคชันภายใน ระบบบริหารจัดการ และเครื่องมือดูแลระบบ
- การพิสูจน์ตัวตนทั้งแบบ Interactive login และแบบ Non-interactive (API key, service account, machine identity)
- การทำงานในสำนักงาน ระยะไกล และผ่านอุปกรณ์ที่ได้รับอนุญาต

## 3. นิยามศัพท์

| คำศัพท์ | ความหมาย |
|---------|----------|
| **Authentication (การพิสูจน์ตัวตน)** | กระบวนการยืนยันว่าผู้ใช้หรือระบบเป็นตัวตนที่อ้างจริง |
| **MFA (Multi-Factor Authentication)** | การพิสูจน์ตัวตนด้วยปัจจัยอย่างน้อย 2 ประเภทจากสิ่งที่รู้ / สิ่งที่มี / สิ่งที่เป็น |
| **Password / Passphrase** | ความลับที่ผู้ใช้ใช้เป็นปัจจัยประเภท “สิ่งที่รู้” |
| **Privileged Account** | บัญชีที่มีสิทธิสูง เช่น Administrator, root, Domain Admin, Cloud Owner |
| **Service Account** | บัญชีที่ใช้โดยระบบหรือบริการ ไม่ใช่บุคคล |
| **SSO (Single Sign-On)** | การเข้าสู่ระบบครั้งเดียวเพื่อเข้าถึงหลายแอปพลิเคชัน |
| **IdP (Identity Provider)** | ระบบศูนย์กลางที่ออกและตรวจสอบตัวตน เช่น Microsoft Entra ID, Okta |
| **Credential Stuffing** | การนำชุดชื่อผู้ใช้/รหัสผ่านที่รั่วจากที่อื่นมาลองเข้าสู่ระบบ |

---

## 4. หลักการทั่วไป

1. **Identity ต่อบุคคล** — บัญชีผู้ใช้ต้องระบุตัวบุคคลได้ ห้ามใช้บัญชีร่วมกัน ยกเว้นได้รับอนุมัติเป็นลายลักษณ์อักษรและมีมาตรการชดเชย
2. **Least Privilege** — ให้สิทธิ์เท่าที่จำเป็นต่องาน
3. **Defense in Depth** — รหัสผ่านอย่างเดียวไม่เพียงพอสำหรับระบบเสี่ยงสูง ต้องใช้ MFA
4. **Assume Breach** — ออกแบบให้ตรวจจับและจำกัดความเสียหายเมื่อข้อมูลรับรองรั่วไหล
5. **Centralize Identity** — ใช้ IdP / SSO เป็นหลัก และลดบัญชี local ที่กระจายอยู่ตามระบบ

## 5. ข้อกำหนดรหัสผ่าน (Password Requirements)

### 5.1 ความยาวและความซับซ้อนขั้นต่ำ

| ประเภทบัญชี | ความยาวขั้นต่ำ | ข้อกำหนดอักขระ | หมายเหตุ |
|-------------|----------------|-----------------|----------|
| ผู้ใช้งานทั่วไป | **อย่างน้อย 12 ตัวอักษร** | แนะนำให้มีตัวพิมพ์ใหญ่ ตัวพิมพ์เล็ก ตัวเลข และอักขระพิเศษอย่างน้อย 3 ใน 4 กลุ่ม | อนุญาต passphrase ที่ยาวและจำง่าย |
| บัญชีสิทธิพิเศษ | **อย่างน้อย 16 ตัวอักษร** | ต้องมีอย่างน้อย 3 ใน 4 กลุ่มอักขระ | ควรสุ่มและเก็บใน password vault |
| บัญชีบริการ / ระบบ | **อย่างน้อย 20 ตัวอักษร** หรือใช้คีย์/ใบรับรองแทน | สุ่มทั้งหมด ห้ามตั้งเองแบบคาดเดาได้ | หมุนเวียนตามรอบที่กำหนด |
| Wi-Fi / Shared technical secret | ตามระดับความเสี่ยง แต่ไม่ต่ำกว่า 16 ตัวอักษร | สุ่ม | จำกัดผู้เข้าถึงและทบทวนเป็นระยะ |

> หากระบบรองรับความยาวได้จำกัดและต่ำกว่าเกณฑ์ ต้องขออนุมัติยกเว้น พร้อมใช้ MFA และมาตรการชดเชย

### 5.2 สิ่งที่ห้ามใช้เป็นรหัสผ่าน

ห้ามใช้รหัสผ่านที่มีลักษณะดังต่อไปนี้

1. คำง่าย ๆ ชื่อบุคคล ชื่อองค์กร ชื่อระบบ วันที่เกิด เบอร์โทร หรือลำดับแป้นพิมพ์ เช่น `Password123`, `P@ssw0rd`, `Company2024`, `qwerty`
2. รหัสผ่านเดียวกับบัญชีส่วนตัวภายนอก (อีเมลส่วนตัว โซเชียลมีเดีย ธนาคาร ฯลฯ)
3. รหัสผ่านที่เคยปรากฏในฐานข้อมูลการรั่วไหล (known breached passwords) หากระบบตรวจสอบได้
4. รหัสผ่านซ้ำกับบัญชีอื่นในองค์กร ในกรณีที่ไม่ได้ใช้ SSO/password manager ที่ควบคุมได้
5. ค่าเริ่มต้นจากผู้ผลิต (default password) — ต้องเปลี่ยนก่อนใช้งานจริง

### 5.3 อายุรหัสผ่านและการเปลี่ยนรหัสผ่าน

| กรณี | ข้อกำหนด |
|------|----------|
| ผู้ใช้งานทั่วไปที่มี MFA | **ไม่บังคับหมุนเวียนตามรอบเวลา** หากไม่มีความเสี่ยงเพิ่ม — ให้เปลี่ยนเมื่อมีเหตุ |
| ผู้ใช้งานทั่วไปที่ไม่มี MFA (ระบบที่ยกเว้น) | เปลี่ยนอย่างน้อยทุก **90 วัน** |
| บัญชีสิทธิพิเศษ | เปลี่ยนอย่างน้อยทุก **90 วัน** หรือทันทีเมื่อมีเหตุเสี่ยง |
| เมื่อสงสัยว่ารหัสผ่านรั่ว / ถูกแชร์ / ถูกฟิชชิง | **เปลี่ยนทันที** และแจ้งฝ่าย IT |
| บัญชีบริการ | หมุนเวียนอย่างน้อยทุก **180 วัน** หรือใช้ certificate/managed identity แทน |

ระบบต้องป้องกันการตั้งรหัสผ่านใหม่ที่เหมือนรหัสผ่านล่าสุดอย่างน้อย **5 ครั้ง** (password history)

### 5.4 การจัดเก็บและการส่งผ่านรหัสผ่าน

1. ระบบต้อง **ไม่เก็บรหัสผ่านเป็นข้อความชัดเจน (plaintext)**
2. เก็บเฉพาะค่า hash ที่เหมาะสม เช่น **bcrypt, scrypt, Argon2 หรือ PBKDF2** พร้อม salt (ห้ามใช้ MD5 / SHA-1 แบบเดี่ยวสำหรับรหัสผ่าน)
3. ส่งรหัสผ่านผ่านช่องทางเข้ารหัสเท่านั้น (เช่น TLS 1.2+)
4. ห้ามส่งรหัสผ่านผ่านอีเมล แชท หรือ SMS เป็นกิจวัตร ยกเว้นรหัสชั่วคราวครั้งแรกที่มีอายุสั้นและบังคับเปลี่ยนทันที
5. ห้ามฝังรหัสผ่าน API key หรือ secret ในซอร์สโค้ด สคริปต์ หรือไฟล์ config ที่ไม่มีการป้องกัน

### 5.5 รหัสผ่านชั่วคราว (Temporary / Initial Password)

1. ต้องสุ่มและมีอายุสั้น (แนะนำไม่เกิน 24 ชั่วโมง)
2. ใช้งานได้ครั้งเดียว หรือบังคับเปลี่ยนเมื่อเข้าสู่ระบบครั้งแรก
3. ส่งผ่านช่องทางที่แยกจากชื่อผู้ใช้หากเป็นไปได้
4. หากไม่ถูกใช้ภายในกำหนด ต้องหมดอายุและออกใหม่

## 6. การพิสูจน์ตัวตนหลายปัจจัย (MFA)

### 6.1 ระบบที่ต้องเปิดใช้ MFA บังคับ

ต้องเปิด MFA สำหรับอย่างน้อยดังนี้

1. อีเมลองค์กรและชุดสำนักงานคลาวด์ (เช่น Microsoft 365 / Google Workspace)
2. VPN / การเข้าถึงเครือข่ายระยะไกล
3. ระบบคลาวด์บริหารจัดการ (AWS, Azure, GCP และคอนโซลเทียบเท่า)
4. บัญชีสิทธิพิเศษทุกประเภท
5. ระบบที่มีข้อมูลส่วนบุคคล ข้อมูลการเงิน หรือข้อมูลระดับลับขึ้นไป
6. ระบบต้นทางของซอร์สโค้ด การ Deploy และการบริหารเซิร์ฟเวอร์
7. SSO / IdP ขององค์กร

### 6.2 วิธีการ MFA ที่ยอมรับ

เรียงจากแนะนำมากไปน้อย

| ระดับ | วิธี | สถานะ |
|-------|------|--------|
| 1 (แนะนำ) | Passkey / FIDO2 / Security Key, Certificate-based auth | อนุญาตและส่งเสริม |
| 2 | Authenticator app (TOTP) หรือ Push notification จากแอปที่องค์กรอนุมัติ | อนุญาตเป็นค่าเริ่มต้น |
| 3 | SMS OTP / Voice OTP | **อนุญาตเฉพาะเมื่อวิธีอื่นใช้ไม่ได้** และควรมีแผนเลิกใช้ |
| — | การส่งรหัสผ่านซ้ำทางอีเมล หรือคำถามความปลอดภัยเพียงอย่างเดียว | **ไม่อนุญาต** ให้เป็นปัจจัยที่สอง |

### 6.3 ข้อกำหนดการใช้งาน MFA

1. ผู้ใช้งานต้องลงทะเบียน MFA ภายในกำหนดที่ฝ่าย IT ระบุ เมื่อได้รับบัญชี
2. ห้ามปิด MFA ด้วยตนเองโดยไม่ได้รับอนุมัติ
3. อุปกรณ์ที่ใช้รับ MFA ต้องอยู่ในความครอบครองของผู้ใช้เจ้าของบัญชี
4. ควรลงทะเบียนวิธีสำรองอย่างน้อย 1 วิธี (เช่น security key สำรอง) และเก็บอย่างปลอดภัย
5. หากทำ MFA หายหรือเปลี่ยนเครื่อง ต้องยืนยันตัวตนกับ Helpdesk / IT ตามขั้นตอนกู้คืนที่กำหนด

## 7. การบริหารบัญชีและการเข้าสู่ระบบ

### 7.1 การสร้างและปิดบัญชี

1. สร้างบัญชีเมื่อมีคำขอที่ได้รับอนุมัติและระบุบทบาทชัดเจน
2. ใช้บัญชีบุคคลธรรมดาสำหรับงานประจำวัน และแยกบัญชีสิทธิพิเศษออกต่างหาก
3. ปิดหรือระงับบัญชีทันทีเมื่อลาออก หมดสัญญา ย้ายหน่วยงาน หรือขาดการใช้งานเกินกำหนด
4. ทบทวนบัญชีและสิทธิ์อย่างน้อยทุก **90 วัน** สำหรับบัญชีทั่วไป และทุก **30–90 วัน** สำหรับบัญชีสิทธิพิเศษ

### 7.2 การล็อกบัญชีและการป้องกันการโจมตี

| รายการ | ค่าแนะนำขั้นต่ำ |
|--------|----------------|
| จำนวนครั้งที่ใส่รหัสผ่านผิดติดต่อกัน | ล็อกชั่วคราวหลัง **5 ครั้ง** |
| ระยะเวลาล็อก | อย่างน้อย **15 นาที** หรือจนกว่า IT จะปลดล็อก |
| การแจ้งเตือน | แจ้งผู้ใช้/IT เมื่อพบการพยายามเข้าสู่ระบบผิดปกติ |
| Session timeout | ตามความเสี่ยงของระบบ โดยระบบสำคัญแนะนำ **15–30 นาที** ที่ไม่มีการใช้งาน |
| Concurrent sessions | จำกัดตามความจำเป็นของระบบ |

### 7.3 การเข้าถึงระยะไกล

1. ต้องผ่านช่องทางที่องค์กรอนุมัติ (VPN หรือ Zero Trust access)
2. บังคับ MFA ทุกครั้ง
3. ห้ามเปิด RDP/SSH ตรงสู่สาธารณะอินเทอร์เน็ตโดยไม่มีชั้นป้องกันเพิ่มเติม
4. บันทึก log การเข้าถึงระยะไกลไว้ตรวจสอบได้

## 8. บัญชีสิทธิพิเศษ (Privileged Access)

1. ใช้บัญชีสิทธิพิเศษเฉพาะเมื่องานจำเป็น และกลับไปใช้บัญชีปกติเมื่อเสร็จ
2. เก็บรหัสผ่านบัญชีสิทธิพิเศษในระบบ Password Vault / PAM ที่องค์กรกำหนด
3. เปิดการบันทึก session หรือ audit log สำหรับกิจกรรมสิทธิพิเศษตามที่ระบบรองรับ
4. ห้ามใช้บัญชีสิทธิพิเศษกับอีเมล ท่องเว็บ หรืองานทั่วไป
5. บัญชี Domain Admin / Cloud Root ต้องมีจำนวนจำกัด มี MFA แข็งแรง และมีรายชื่อเจ้าของชัดเจน

---

## 9. บัญชีบริการ API Key และ Non-Human Identity

1. ห้ามใช้บัญชีบุคคลสำหรับรันบริการอัตโนมัติ หากสามารถสร้าง service account ได้
2. ให้สิทธิ์แคบที่สุด และแยก secret ต่อระบบ/สภาพแวดล้อม
3. เก็บ secret ในระบบ Secrets Manager / Vault เท่านั้น
4. หมุนเวียนคีย์เป็นระยะ และเพิกถอนทันทีเมื่อไม่ใช้งานหรือสงสัยว่ารั่วไหล
5. ห้าม commit secret ขึ้น Git หรือระบบควบคุมเวอร์ชัน
6. แนะนำให้ใช้ workload identity / managed identity / certificate แทนรหัสผ่านระยะยาวเมื่อทำได้

---

## 10. Single Sign-On และการรวมศูนย์ตัวตน

1. ระบบใหม่ควรรองรับ SSO ผ่าน IdP ขององค์กรเป็นอันดับแรก
2. ลดจำนวนบัญชี local username/password ที่ซ้ำซ้อน
3. เมื่อยกเลิกสิทธิ์ที่ IdP ต้องตัดการเข้าถึงระบบที่เชื่อม SSO ตามไปด้วย
4. การออกจากระบบ (logout) และการหมดอายุ session ต้องสอดคล้องกับระดับความเสี่ยงของแอป

---

## 11. Password Manager และการเก็บรหัสผ่านของผู้ใช้

1. องค์กรควรจัดหาหรืออนุมัติ Password Manager สำหรับงาน
2. อนุญาตให้บันทึกรหัสผ่านใน Password Manager ที่ได้รับอนุมัติเท่านั้น
3. ห้ามบันทึกรหัสผ่านในไฟล์ข้อความ สเปรดชีต โน้ตติดหน้าจอ หรือเบราว์เซอร์ส่วนตัวที่ไม่มีการป้องกันเพียงพอสำหรับข้อมูลองค์กร
4. Master password ของ Password Manager ต้องแข็งแรงและเปิด MFA หากรองรับ

---

## 12. การกู้คืนบัญชีและการรีเซ็ตรหัสผ่าน

1. ต้องยืนยันตัวตนของผู้ขอรีเซ็ตก่อนดำเนินการ เช่น ตรวจบัตรพนักงาน หัวหน้างานรับรอง หรือช่องทางที่กำหนด
2. ห้ามรีเซ็ตรหัสผ่านตามคำขอทางโทรศัพท์/แชทโดยไม่มีขั้นตอนยืนยันตัวตน
3. รหัสผ่านใหม่ต้องเป็นรหัสชั่วคราวและบังคับเปลี่ยนทันที
4. บันทึกการรีเซ็ตทุกรายการเพื่อการตรวจสอบ
5. กรณีถูกฟิชชิงหรือยึดบัญชี ให้รีเซ็ต ถอน session ตรวจกิจกรรมต้องสงสัย และประเมินการรั่วไหลของข้อมูล

---

## 13. ข้อกำหนดสำหรับผู้ใช้งาน (สิ่งที่ต้องปฏิบัติ)

1. ตั้งรหัสผ่านตามเกณฑ์ในมาตรฐานนี้ และไม่แชร์ให้ผู้อื่น
2. เปิดและรักษา MFA ให้พร้อมใช้งานเสมอ
3. ล็อกเครื่องเมื่อไม่อยู่หน้าจอ
4. หากสงสัยว่าบัญชีถูกละเมิด ให้เปลี่ยนรหัสผ่าน แจ้ง IT และหยุดใช้เครื่อง/บัญชีที่เสี่ยง
5. ไม่ป้อนรหัสผ่านในหน้าเว็บที่น่าสงสัย หรือหลังคลิกลิงก์จากอีเมลที่ไม่น่าเชื่อถือ
6. ไม่ใช้รหัสผ่านองค์กรกับบริการส่วนตัว

---

## 14. ข้อกำหนดสำหรับผู้ดูแลระบบและผู้พัฒนา

1. Enforce นโยบายรหัสผ่านและ MFA บนระบบตามมาตรฐานนี้
2. ปิดบัญชี default และเปลี่ยนค่าเริ่มต้นก่อนขึ้นใช้งาน
3. ตรวจสอบ log ความล้มเหลวในการเข้าสู่ระบบเป็นระยะ
4. ใช้ secrets management ในทุกสภาพแวดล้อม
5. ทดสอบการรีเซ็ตรหัสผ่าน การล็อกบัญชี และการหมดอายุ session ก่อนรับระบบเข้าใช้งานจริง
6. เมื่อพบช่องโหว่ด้านการยืนยันตัวตน ให้แก้ไขตามระดับความรุนแรงโดยเร็ว

---

## 15. การยกเว้น (Exceptions)

1. การขอผ่อนผันจากมาตรฐานนี้ต้องระบุระบบ เหตุผล ระยะเวลา มาตรการชดเชยความเสี่ยง และผู้รับผิดชอบ
2. ต้องได้รับอนุมัติจากผู้จัดการฝ่าย IT / ISO และบันทึกไว้เป็นลายลักษณ์อักษร
3. ทบทวนการยกเว้นอย่างน้อยทุก **90 วัน**
4. ตัวอย่างที่ยอมรับได้ชั่วคราว เช่น ระบบมรดก (legacy) ที่ไม่รองรับ MFA แต่มี compensating control เช่น จำกัดเครือข่าย + เฝ้าระวังเข้มข้น

---

## 16. การตรวจสอบและการวัดผล

ฝ่าย IT / ISO ควรติดตามตัวชี้วัดอย่างน้อยดังนี้

| ตัวชี้วัด | เป้าหมายแนะนำ |
|----------|----------------|
| อัตราการเปิดใช้ MFA บนระบบบังคับ | **100%** ของบัญชีที่ใช้งานอยู่ |
| บัญชีที่ไม่มีการใช้งานเกินกำหนด | ถูกระงับ/ลบตามรอบทบทวน |
| จำนวนเหตุ credential-related incident | ลดลงเมื่อเทียบรายไตรมาส และมี root cause |
| บัญชีสิทธิพิเศษที่ไม่อยู่ใน vault | **0** |
| การพบ secret ในโค้ด/ที่เก็บสาธารณะ | แก้ไขและเพิกถอนภายในกำหนด |

---

## 17. การบังคับใช้

การฝ่าฝืนมาตรฐานนี้อาจถูกระงับสิทธิ์การใช้งาน ดำเนินการทางวินัยตามระเบียบองค์กร และ/หรือดำเนินการตามกฎหมายหากก่อให้เกิดความเสียหาย โดยเฉพาะกรณีแชร์รหัสผ่าน จงใจปิด MFA หรือเก็บ secret ในที่ที่ไม่ปลอดภัยจนเกิดเหตุรั่วไหล

- ISO/IEC 27001:2022 / ISO/IEC 27002:2022 (A.5.15, A.5.16, A.5.17, A.8.5 ฯลฯ)
- NIST SP 800-63B Digital Identity Guidelines
