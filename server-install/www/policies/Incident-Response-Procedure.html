Incident-Response-Procedure

ขั้นตอนการจัดการเหตุการณ์ด้านความปลอดภัย

Security Incident Response Procedure

รายการ รายละเอียด
รหัสเอกสาร PROC-IR-001
เวอร์ชัน 1.0
วันที่มีผลบังคับใช้ [ระบุวันที่]
เอกสารแม่ POL-ITSEC-001 นโยบายการรักษาความปลอดภัยระบบเทคโนโลยีสารสนเทศ
เอกสารที่เกี่ยวข้อง STD-ITSEC-001, STD-ITSEC-002, POL-PDPA-001
ผู้อนุมัติ [ผู้บริหารฝ่ายเทคโนโลยีสารสนเทศ / ISO]
ผู้รับผิดชอบ Information Security Officer / ฝ่ายเทคโนโลยีสารสนเทศ
รอบทบทวน อย่างน้อยปีละ 1 ครั้ง หรือหลังเกิดเหตุร้ายแรง
การจัดประเภทเอกสาร ภายในองค์กร (Internal)

1. วัตถุประสงค์

ขั้นตอนนี้อธิบายวิธีปฏิบัติเมื่อเกิดหรือสงสัยว่าเกิดเหตุการณ์ด้านความปลอดภัยของสารสนเทศ เพื่อ

  1. ตรวจจับ รายงาน และตอบสนองต่อเหตุการณ์ได้อย่างรวดเร็วและเป็นระบบ
  2. จำกัดความเสียหาย กู้คืนการดำเนินงาน และรักษาหลักฐานที่เกี่ยวข้อง
  3. สื่อสารกับผู้เกี่ยวข้องภายในและภายนอกอย่างเหมาะสม
  4. ปฏิบัติตามข้อกำหนดของ พ.ร.บ.คุ้มครองข้อมูลส่วนบุคคล พ.ศ. 2562 และ พ.ร.บ.การรักษาความมั่นคงปลอดภัยไซเบอร์ พ.ศ. 2562 เมื่อเข้าเกณฑ์
  5. บันทึกบทเรียนและปรับปรุงมาตรการป้องกันอย่างต่อเนื่อง

2. ขอบเขต

ขั้นตอนนี้ใช้กับ

  • เหตุการณ์หรือเหตุต้องสงสัยที่กระทบหรืออาจกระทบความลับ ความถูกต้องครบถ้วน หรือความพร้อมใช้งานของข้อมูล/ระบบองค์กร
  • ระบบ เครือข่าย คลาวด์ อุปกรณ์ปลายทาง บัญชีผู้ใช้ ข้อมูล และบริการของผู้ให้บริการภายนอกที่เกี่ยวข้องกับองค์กร
  • พนักงาน ผู้รับจ้าง พันธมิตร และบุคคลภายนอกที่ใช้งานหรือเชื่อมต่อกับระบบขององค์กร

ตัวอย่างเหตุที่อยู่ในขอบเขต - มัลแวร์ / แรนซัมแวร์ / การฝังโค้ดไม่พึงประสงค์ - ฟิชชิง การยึดบัญชี การเดารหัสผ่าน - การเข้าถึงโดยไม่ได้รับอนุญาต การใช้สิทธิ์เกินขอบเขต - การรั่วไหลหรือสูญหายของข้อมูล รวมถึงข้อมูลส่วนบุคคล - การโจมตีปฏิเสธการให้บริการ (DoS/DDoS) - การสูญหายหรือถูกขโมยของอุปกรณ์ที่มีข้อมูลองค์กร - การพบช่องโหว่วิกฤตที่กำลังถูกโจมตีหรือมีหลักฐานถูกโจมตีแล้ว

3. นิยามศัพท์

คำศัพท์ ความหมาย
Security Event เหตุการณ์ที่สังเกตได้ในระบบ เช่น login ล้มเหลว การเปลี่ยนแปลงค่าคอนฟิก
Security Incident Event ที่ยืนยันหรือมีเหตุอันควรเชื่อว่ากระทบต่อความมั่นคงปลอดภัยสารสนเทศ
Personal Data Breach การละเมิดมาตรการรักษาความมั่นคงปลอดภัยที่ทำให้เกิดการสูญหาย เข้าถึง ใช้ เปลี่ยนแปลง แก้ไข หรือเปิดเผยข้อมูลส่วนบุคคลโดยไม่ชอบด้วยกฎหมาย
Incident Commander (IC) ผู้ควบคุมการตอบสนองเหตุในแต่ละเคส
CSIRT / IR Team ทีมตอบสนองเหตุการณ์ด้านความปลอดภัย
IoC (Indicator of Compromise) ร่องรอยบ่งชี้การถูกโจมตี เช่น hash, IP, domain, บัญชีผิดปกติ
Containment การจำกัดขอบเขตความเสียหายไม่ให้ขยายต่อ
Eradication การกำจัดสาเหตุ ภัยคุกคาม หรือช่องทางที่ถูกใช้โจมตี
Recovery การกู้คืนระบบและบริการให้กลับสู่ภาวะปกติอย่างปลอดภัย
Post-Incident Review การทบทวนหลังเกิดเหตุเพื่อหาสาเหตุและแนวทางปรับปรุง

4. บทบาทและหน้าที่

บทบาท หน้าที่หลัก
ผู้พบเหตุ / ผู้ใช้งาน แจ้งเหตุทันที ไม่ปกปิด ไม่พยายามทำลายหลักฐาน
Helpdesk / IT Support รับเรื่อง คัดกรองเบื้องต้น เปิดตั๋วงาน และส่งต่อทีม IR
Incident Commander (IC) บริหารเคสทั้งหมด จัดลำดับงาน ตัดสินใจ escalation และปิดเคส
CSIRT / Security Team วิเคราะห์ กักกัน กำจัด กู้คืน และรวบรวมหลักฐาน
System Owner / Data Owner ให้ข้อมูลระบบ/ข้อมูลธุรกิจ อนุมัติ downtime หรือมาตรการฉุกเฉินที่เกี่ยวข้อง
DPO / ฝ่ายกฎหมาย ประเมินเหตุละเมิดข้อมูลส่วนบุคคล การแจ้งตามกฎหมาย และประเด็นสัญญา
ฝ่ายสื่อสารองค์กร / ผู้บริหาร สื่อสารภายใน/ภายนอกตามที่ได้รับอนุมัติ
ผู้ให้บริการภายนอก ให้ความร่วมมือตามสัญญา เมื่อระบบหรือข้อมูลอยู่ในความดูแลของตน

5. ระดับความรุนแรง (Severity)

ระดับ ชื่อ ตัวอย่าง เป้าหมายเริ่มตอบสนอง เป้าหมายกักกันเบื้องต้น
P1 Critical แรนซัมแวร์กระจายตัว, ยึดบัญชี Domain Admin, ข้อมูลลับที่สุดรั่วไหลยืนยันแล้ว, ระบบสำคัญหยุดทั้งองค์กร 15 นาที 1 ชั่วโมง
P2 High ยึดบัญชีผู้ใช้สำคัญ, มัลแวร์บนเซิร์ฟเวอร์, สงสัยข้อมูลส่วนบุคคลรั่ว, ระบบสำคัญเสื่อมบางส่วน 30 นาที 4 ชั่วโมง
P3 Medium ฟิชชิงที่มีผู้คลิก, มัลแวร์บนเครื่องเดียวที่กักกันได้, การตั้งค่าผิดพลาดที่มีความเสี่ยง 4 ชั่วโมง 1 วันทำการ
P4 Low สแปม/ฟิชชิงที่ยังไม่สำเร็จ, นโยบายถูกละเมิดเล็กน้อย, สัญญาณเตือนที่พิสูจน์แล้วว่า false positive 1 วันทำการ ตามแผนแก้ไข

IC สามารถปรับระดับได้เมื่อมีข้อมูลใหม่ และต้องบันทึกเหตุผลการปรับทุกครั้ง

6. ช่องทางแจ้งเหตุ

ประเภท ช่องทาง เวลา
เหตุด่วน P1–P2 [ระบุ: Hotline / เบอร์ฉุกเฉิน / Chat on-call] 24×7
เหตุทั่วไป [ระบุ: Helpdesk / security@company] เวลาทำการ หรือตามที่กำหนด
เหตุข้อมูลส่วนบุคคล [ระบุ: DPO] พร้อมสำเนาถึง Security โดยเร็วที่สุด
นอกเวลาทำการ [ระบุ: On-call rota] ตามตารางเวร

ข้อมูลที่ควรแจ้งตอนแรก

  1. วันเวลาที่พบเหตุ และเวลาที่สงสัยว่าเริ่มต้น
  2. ระบบ บัญชี อุปกรณ์ หรือข้อมูลที่เกี่ยวข้อง
  3. สิ่งที่เกิดขึ้น / สิ่งที่สังเกตได้
  4. ผลกระทบเบื้องต้น (หยุดบริการ ข้อมูลรั่ว สงสัยถูกยึดบัญชี ฯลฯ)
  5. การดำเนินการไปแล้ว (ถ้ามี) เช่น ปิดเครื่อง เปลี่ยนรหัสผ่าน
  6. ชื่อผู้แจ้งและช่องทางติดต่อกลับ

7. ขั้นตอนการดำเนินงาน (Incident Lifecycle)

1. Detect/Report → 2. Triage/Classify → 3. Contain
        → 4. Investigate → 5. Eradicate → 6. Recover
        → 7. Communicate/Notify → 8. Close & Lessons Learned

7.1 การตรวจจับและการรายงาน (Detect / Report)

  1. ผู้พบเหตุแจ้งผ่านช่องทางที่กำหนด โดยเร็ว
  2. ห้ามปกปิดเหตุการณ์
  3. โดยหลักแล้ว อย่าปิดเครื่องทันที หากยังสามารถรักษาหลักฐานได้ ยกเว้นเหตุกำลังขยายตัวรุนแรงและ IC สั่งให้ตัดการเชื่อมต่อ
  4. Helpdesk เปิด Incident Ticket ภายในเวลาเป้าหมายตามระดับความรุนแรง

7.2 การคัดกรองและจัดประเภท (Triage / Classify)

IC หรือเจ้าหน้าที่ที่ได้รับมอบหมายดำเนินการ

  1. ยืนยันว่าเป็น Security Incident หรือเป็น Event/False Positive
  2. กำหนดระดับความรุนแรง P1–P4
  3. ระบุระบบ ข้อมูล และธุรกิจที่ได้รับผลกระทบ
  4. ตัดสินใจว่าต้องเรียกทีมขยาย (DPO, กฎหมาย, ผู้บริหาร, vendor) หรือไม่
  5. บันทึก timeline เริ่มต้นของเคส

7.3 การกักกัน (Containment)

เลือกมาตรการตามความเหมาะสม โดยไม่ทำลายหลักฐานโดยไม่จำเป็น

มาตรการระยะสั้น - แยกเครื่องออกจากเครือข่าย / ปิดพอร์ต / block บัญชี - รีเซ็ตรหัสผ่านและถอน session - บล็อก IoC บนไฟร์วอลล์ DNS อีเมลเกตเวย์ - ปิดการแชร์ไฟล์หรือ API ที่เกี่ยวข้อง

มาตรการระยะกลาง - จำกัดการเข้าถึงระบบสำคัญชั่วคราว - เปิดโหมดเฝ้าระวังเข้มข้น - เตรียมช่องทางสื่อสารสำรองหากช่องทางหลักถูกกระทบ

7.4 การสอบสวน (Investigation)

  1. รวบรวม log, alert, ไฟล์ต้องสงสัย, รายการบัญชี และบันทึกการเปลี่ยนแปลง
  2. ระบุ entry point, ขอบเขตการเคลื่อนที่ในเครือข่าย และข้อมูลที่อาจถูกเข้าถึง
  3. ประเมินว่ามีการขโมยข้อมูล การเข้ารหัสไฟล์ หรือการสร้างช่องทางลับหรือไม่
  4. รักษาห่วงโซ่การครอบครองหลักฐาน (chain of custody) หากมีแนวโน้มใช้ทางกฎหมาย
  5. อัปเดต timeline และสถานะให้ผู้เกี่ยวข้องทราบเป็นระยะ

7.5 การกำจัดสาเหตุ (Eradication)

  1. ลบมัลแวร์ ปิดช่องโหว่ เพิกถอน credential ที่รั่ว
  2. แพตช์ระบบ ปรับค่าคอนฟิก และลบบัญชีไม่ชอบมาพากล
  3. ตรวจสอบว่าระบบอื่นถูกกระทบด้วยหรือไม่ก่อนประกาศว่ากำจัดแล้ว
  4. ในกรณีแรนซัมแวร์ โดยหลักให้กู้จากสำรองที่สะอาด หลีกเลี่ยงการเจรจาจ่ายค่าไถ่ เว้นแต่ผู้บริหารและฝ่ายกฎหมายพิจารณาเป็นกรณีพิเศษ

7.6 การกู้คืน (Recovery)

  1. กู้คืนจากแหล่งสำรองที่ตรวจสอบแล้วว่าปลอดภัย
  2. เฝ้าระวังเข้มข้นหลังเปิดบริการกลับ
  3. ยืนยันกับ System Owner ว่าฟังก์ชันธุรกิจกลับมาใช้งานได้
  4. ค่อย ๆ ปลดมาตรการฉุกเฉินเมื่อความเสี่ยงลดลง
  5. บันทึกเวลาที่บริการกลับสู่ภาวะปกติ

7.7 การสื่อสารและการแจ้งเตือน (Communication / Notify)

  1. สื่อสารภายในตามระดับความรุนแรง โดยใช้ช่องทางที่อนุมัติ
  2. ห้าม พนักงานทั่วไปโพสต์หรือให้สัมภาษณ์ภายนอกเกี่ยวกับเหตุโดยไม่ได้รับมอบหมาย
  3. การแจ้งลูกค้า คู่ค้า สื่อมวลชน หรือหน่วยงานรัฐ ต้องผ่านผู้บริหาร / กฎหมาย / DPO ตามกรณี
  4. หากเป็น Personal Data Breach ให้ดำเนินการตามข้อ 8

7.8 การปิดเคสและบทเรียน (Close & Lessons Learned)

  1. ปิดเคสเมื่อภัยคุกคามถูกกำจัด บริการกลับมา และงานติดตามถูกมอบหมายแล้ว
  2. จัดทำรายงานสรุปเหตุ (Incident Report)
  3. ทำ Post-Incident Review สำหรับ P1–P2 ทุกเคส และ P3 ตามความเหมาะสม
  4. ติดตาม corrective / preventive actions จนเสร็จ
  5. อัปเดต playbook กฎตรวจจับ และการอบรมหากจำเป็น

8. กรณีละเมิดข้อมูลส่วนบุคคล (PDPA Breach Handling)

เมื่อสงสัยว่ามีข้อมูลส่วนบุคคลรั่วไหล สูญหาย หรือถูกเข้าถึงโดยไม่ชอบ ให้ดำเนินการเพิ่มเติมดังนี้

  1. แจ้ง DPO / ฝ่ายกฎหมาย ทันทีที่ทราบ
  2. ประเมินอย่างน้อยในประเด็น
    • ประเภทและปริมาณข้อมูล
    • จำนวนเจ้าของข้อมูลที่ได้รับผลกระทบ
    • ความเสี่ยงต่อสิทธิและเสรีภาพของบุคคล
    • มาตรการที่ทำไปแล้วเพื่อลดผลกระทบ
  3. หากเข้าเกณฑ์ต้องแจ้ง สำนักงานคณะกรรมการคุ้มครองข้อมูลส่วนบุคคล ให้เตรียมการแจ้ง โดยไม่ชักช้า และภายใน 72 ชั่วโมง นับแต่ทราบเหตุ ตามที่กฎหมายกำหนด
  4. พิจารณาการแจ้งเจ้าของข้อมูลเมื่อเหตุมีโอกาสสูงที่จะกระทบสิทธิและเสรีภาพ
  5. บันทึกข้อเท็จจริง การประเมิน และการตัดสินใจไว้เป็นหลักฐาน

รายละเอียดการแจ้งและแบบฟอร์มภายในให้เป็นไปตาม POL-PDPA-001 และแนวทางของ DPO

9. Playbook ย่อตามประเภทเหตุ

9.1 ฟิชชิง / ยึดบัญชี

  1. ให้ผู้ใช้หยุดโต้ตอบกับข้อความนั้น และส่งตัวอย่างให้ Security
  2. บล็อก sender/URL/attachment
  3. หากมีการป้อนรหัสผ่านหรือ MFA ถูกใช้แล้ว → รีเซ็ตรหัสผ่าน ถอน session ทบทวน MFA ตรวจกิจกรรมต้องสงสัย
  4. ตรวจว่ามีการส่งต่อภายในหรือเข้าถึงไฟล์สำคัญหรือไม่

9.2 มัลแวร์ / แรนซัมแวร์

  1. แยกเครื่อง/เซิร์ฟเวอร์ออกจากเครือข่ายทันทีตามคำสั่ง IC
  2. อย่ารีสตาร์ทหรือลบไฟล์เองหากยังไม่ได้ถ่ายภาพหลักฐาน
  3. ระบุขอบเขตการติดเชื้อจาก EDR/log
  4. กู้จากสำรองที่สะอาด แพตช์ช่องทางเข้า และเฝ้าระวังซ้ำ

9.3 อุปกรณ์สูญหายหรือถูกขโมย

  1. ระงับบัญชีที่ผูกกับอุปกรณ์และถอน session
  2. ล็อกหรือลบข้อมูลระยะไกลหากทำได้
  3. ประเมินว่ามีข้อมูลระดับลับขึ้นไปอยู่ในเครื่องหรือไม่ และมีการเข้ารหัสดิสก์หรือไม่
  4. เปลี่ยนรหัสผ่านที่เกี่ยวข้องและแจ้ง DPO หากมีความเสี่ยงข้อมูลส่วนบุคคล

9.4 การโจมตีบริการจนล่ม (DoS/DDoS)

  1. ยืนยันอาการและแยกจากเหตุล่มจากการตั้งค่า/ซ่อมบำรุง
  2. เปิดมาตรการบรรเทาบนเครือข่าย/CDN/ผู้ให้บริการ
  3. สื่อสารสถานะบริการกับผู้ใช้ภายในตามความเหมาะสม
  4. เก็บ traffic sample และ timeline เพื่อวิเคราะห์ภายหลัง

9.5 การรั่วไหลของข้อมูล / ส่งไฟล์ผิดคน

  1. ขอให้ผู้รับลบข้อมูลหากติดต่อได้ และเพิกถอนลิงก์แชร์ทันที
  2. ระบุประเภทข้อมูลและจำนวนผู้ได้รับผลกระทบ
  3. ประสาน Data Owner และ DPO
  4. ประเมินความจำเป็นในการแจ้งตามกฎหมายและสัญญา

10. การรักษาหลักฐาน

  1. บันทึกวันเวลา (ระบุเขตเวลา) ผู้เก็บ และแหล่งที่มาของหลักฐานทุกชิ้น
  2. เก็บสำเนา log ดิบ ภาพหน่วยความจำ หรืออิมเมจดิสก์ตามความจำเป็นของเคส
  3. จำกัดสิทธิ์เข้าถึงคลังหลักฐานเฉพาะทีมที่เกี่ยวข้อง
  4. ห้ามแก้ไขไฟล์ต้นฉบับโดยไม่จำเป็น ให้ทำงานบนสำเนา
  5. หากอาจดำเนินคดี ให้ประสานฝ่ายกฎหมายก่อนเคลื่อนย้ายหรือเปิดเผยหลักฐานภายนอก

11. Escalation Matrix

สถานการณ์ ต้องแจ้งเพิ่ม
P1 ทุกกรณี ผู้บริหาร IT, ISO, System Owner, On-call executive ตามตาราง
มีหรือสงสัยข้อมูลส่วนบุคคลรั่ว DPO / ฝ่ายกฎหมาย
กระทบลูกค้าหรือบริการภายนอก ผู้บริหารธุรกิจ + ฝ่ายสื่อสาร
กระทบผู้ให้บริการภายนอก Vendor manager + ข้อสัญญาที่เกี่ยวข้อง
มีแนวโน้มผิดกฎหมายอาญา/ไซเบอร์ร้ายแรง ฝ่ายกฎหมาย เพื่อพิจารณาแจ้งหน่วยงานรัฐ

12. แบบฟอร์มและบันทึกที่ต้องมี

ใช้หรือสร้างบันทึกอย่างน้อยดังนี้

รหัส (ตัวอย่าง) ชื่อ
FORM-IR-001 แบบแจ้งเหตุการณ์ด้านความปลอดภัย
FORM-IR-002 บันทึก timeline และตัดสินใจของ IC
FORM-IR-003 ทะเบียนหลักฐาน (Evidence Log)
FORM-IR-004 รายงานสรุปเหตุการณ์ (Incident Report)
FORM-IR-005 บันทึก Post-Incident Review และ Action Plan

หัวข้อขั้นต่ำในรายงานสรุปเหตุ

  1. รหัสเคส ระดับความรุนแรง ช่วงเวลาเกิดเหตุ
  2. สรุปเหตุการณ์และผลกระทบ
  3. Root cause (ถ้าทราบ)
  4. การดำเนินการหลักและเวลาสำคัญ
  5. ข้อมูล/ระบบที่เกี่ยวข้อง
  6. การแจ้งภายนอก (ถ้ามี)
  7. แนวทางป้องกันซ้ำและผู้รับผิดชอบ

13. การทดสอบและฝึกซ้อม

  1. ทบทวนขั้นตอนนี้อย่างน้อยปีละ 1 ครั้ง
  2. จัดซ้อมตอบสนองเหตุ (tabletop หรือ simulation) อย่างน้อยปีละ 1 ครั้ง สำหรับสถานการณ์ P1 เช่น แรนซัมแวร์หรือข้อมูลรั่ว
  3. ปรับปรุงช่องทางติดต่อ On-call และ playbook หลังการซ้อมทุกครั้ง

14. ตัวชี้วัด (KPI / Metrics)

ตัวชี้วัด คำอธิบาย
Time to Detect เวลาตั้งแต่เริ่มเหตุจนถูกตรวจพบ/รับแจ้ง
Time to Acknowledge เวลาตั้งแต่รับแจ้งจนมีผู้รับผิดชอบเริ่มดูแล
Time to Contain เวลาจนสามารถกักกันได้สำเร็จ
Time to Recover เวลาจนบริการสำคัญกลับมาใช้งานได้
% เคสที่มี Post-Incident Review โดยเฉพาะ P1–P2 ต้องครบ 100%
Repeat Incident Rate สัดส่วนเหตุซ้ำจากสาเหตุเดิมที่ยังไม่แก้

15. การบังคับใช้

  1. ผู้เกี่ยวข้องทุกคนต้องปฏิบัติตามขั้นตอนนี้
  2. การปกปิดเหตุ การทำลายหลักฐานโดยเจตนา หรือการสื่อสารภายนอกโดยไม่ได้รับอนุญาต ถือเป็นความผิดร้ายแรง
  3. การฝ่าฝืนอาจนำไปสู่มาตรการทางวินัยตามระเบียบองค์กรและการดำเนินการตามกฎหมาย

18. ภาคผนวก ก — สรุปด่วนสำหรับผู้พบเหตุ (One-Page)

  1. อย่าตกใจ และอย่าปกปิด
  2. จดเวลา สิ่งที่เห็น ระบบ/บัญชีที่เกี่ยวข้อง
  3. แจ้ง Hotline / Helpdesk / Security ทันที
  4. อย่าคลิกลิงก์ซ้ำ อย่าส่งต่อไฟล์ต้องสงสัย และอย่าลบหลักฐานเอง
  5. หากสงสัยบัญชีถูกละเมิด ให้แจ้ง IT เพื่อรีเซ็ตและถอน session
  6. รอคำสั่งจากทีม IR ก่อนทำขั้นตอนเพิ่มเติม
