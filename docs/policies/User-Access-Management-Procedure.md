# ขั้นตอนการขอ/เปลี่ยนแปลง/เพิกถอนสิทธิ์ผู้ใช้
## User Access Request, Change, and Revocation Procedure

| รายการ | รายละเอียด |
|--------|------------|
| **รหัสเอกสาร** | PROC-IAM-001 |
| **เวอร์ชัน** | 1.0 |
| **วันที่มีผลบังคับใช้** | [ระบุวันที่] |
| **เอกสารแม่** | POL-ITSEC-001 นโยบายการรักษาความปลอดภัยระบบเทคโนโลยีสารสนเทศ |
| **เอกสารที่เกี่ยวข้อง** | STD-ITSEC-001, STD-ITSEC-002, PROC-IR-001 |
| **ผู้อนุมัติ** | [ผู้บริหารฝ่ายเทคโนโลยีสารสนเทศ / ISO] |
| **ผู้รับผิดชอบ** | ฝ่ายเทคโนโลยีสารสนเทศ / Identity & Access Administrator |
| **รอบทบทวน** | อย่างน้อยปีละ 1 ครั้ง หรือเมื่อมีการเปลี่ยนแปลงที่สำคัญ |
| **การจัดประเภทเอกสาร** | ภายในองค์กร (Internal) |

---

## 1. วัตถุประสงค์

ขั้นตอนนี้อธิบายวิธีปฏิบัติในการขอ เปลี่ยนแปลง ทบทวน และเพิกถอนสิทธิ์การเข้าถึงระบบสารสนเทศ เพื่อ

1. ให้สิทธิ์ตามหลัก **Least Privilege** และ **Need-to-Know**
2. ให้มีการอนุมัติที่ตรวจสอบได้ก่อนเปิดหรือขยายสิทธิ์
3. เพิกถอนสิทธิ์อย่างทันเวลาเมื่อพ้นสภาพ ย้ายหน่วยงาน หรือหมดความจำเป็น
4. ลดความเสี่ยงจากบัญชีค้างสิทธิ์ บัญชีแชร์ และสิทธิพิเศษเกินจำเป็น
5. สนับสนุนการปฏิบัติตาม POL-ITSEC-001 และ STD-ITSEC-001

---

## 2. ขอบเขต

ขั้นตอนนี้ใช้กับ

- บัญชีผู้ใช้บุคคล บัญชีสิทธิพิเศษ บัญชีบริการ และสิทธิ์ตามบทบาท (role/group)
- ระบบขององค์กร เช่น อีเมล SSO VPN ไฟล์แชร์ แอปธุรกิจ ระบบคลาวด์ ระบบ HR/การเงิน และเครื่องมือดูแลระบบ
- พนักงาน ลูกจ้าง ผู้รับเหมา ที่ปรึกษา นักศึกษาฝึกงาน พันธมิตร และบัญชีชั่วคราว
- วงจร Joiner (เข้าใหม่) / Mover (โยกย้าย) / Leaver (พ้นสภาพ)

## 3. นิยามศัพท์

| คำศัพท์ | ความหมาย |
|---------|----------|
| **Access Request** | คำขอเปิดสิทธิ์หรือสร้างบัญชีใหม่ |
| **Access Change** | คำขอเพิ่ม ลด หรือปรับสิทธิ์ของบัญชีที่มีอยู่ |
| **Access Revocation** | การระงับหรือเพิกถอนสิทธิ์/บัญชี |
| **Role-Based Access Control (RBAC)** | การให้สิทธิ์ตามบทบาทงาน |
| **Privileged Access** | สิทธิ์ระดับผู้ดูแลระบบหรือสูงกว่าผู้ใช้ทั่วไป |
| **Joiner / Mover / Leaver** | ผู้เข้าใหม่ / ผู้โยกย้ายหน่วยงานหรือบทบาท / ผู้พ้นสภาพ |
| **SoD (Segregation of Duties)** | การแบ่งแยกหน้าที่เพื่อลดความเสี่ยงจากการทำธุรกรรมคนเดียวครบวงจร |
| **Access Review** | การทบทวนสิทธิ์ที่มีอยู่เป็นระยะ |
| **Birthright Access** | สิทธิ์พื้นฐานที่ให้โดยอัตโนมัติตามประเภทการจ้างงาน เช่น อีเมล ชุดสำนักงาน |

## 4. บทบาทและหน้าที่

| บทบาท | หน้าที่หลัก |
|--------|-------------|
| **ผู้ขอสิทธิ์ (Requester)** | ยื่นคำขอ ระบุเหตุผล ระบบ ระยะเวลา และขอบเขตสิทธิ์ |
| **หัวหน้างานโดยตรง** | ตรวจสอบความจำเป็นทางธุรกิจ และอนุมัติคำขอทั่วไป |
| **เจ้าของระบบ / เจ้าของข้อมูล (System/Data Owner)** | อนุมัติสิทธิ์ในระบบหรือข้อมูลที่รับผิดชอบ โดยเฉพาะระดับลับขึ้นไป |
| **HR** | แจ้งสถานะเข้าใหม่ โยกย้าย ลาออก/หมดสัญญา ให้ IT ทราบตามเวลาที่กำหนด |
| **IT Access Admin** | ดำเนินการสร้าง/ปรับ/เพิกถอนสิทธิ์ บันทึกหลักฐาน และแจ้งผล |
| **ISO / Security** | กำกับมาตรฐาน ทบทวนสิทธิพิเศษ และสุ่มตรวจ |
| **ผู้ใช้งาน** | ใช้สิทธิ์เท่าที่ได้รับ ห้ามแชร์บัญชี และแจ้งเมื่อไม่ต้องการใช้สิทธิ์แล้ว |

---

## 5. หลักการให้สิทธิ์

1. ให้สิทธิ์เท่าที่จำเป็นต่องานปัจจุบันเท่านั้น
2. ใช้ RBAC / กลุ่มสิทธิ์มาตรฐานเป็นหลัก หลีกเลี่ยงสิทธิ์แบบกำหนดเองโดยไม่จำเป็น
3. บัญชีต้องเป็นรายบุคคล ห้ามใช้บัญชีร่วม ยกเว้นได้รับอนุมัติเป็นลายลักษณ์อักษรและมีมาตรการชดเชย
4. แยกบัญชีงานประจำวันออกจากบัญชีสิทธิพิเศษ
5. สิทธิ์ชั่วคราวต้องกำหนดวันหมดอายุทุกครั้ง
6. การอนุมัติต้องแยกจากผู้ดำเนินการให้สิทธิ์ตามหลัก SoD ให้ได้มากที่สุด
7. ห้ามคัดลอกสิทธิ์จากบุคคลอื่นทั้งชุดโดยไม่ตรวจสอบความจำเป็น (ห้าม “copy all access” แบบไม่ได้กลั่นกรอง)

## 6. ประเภทคำขอและผู้อนุมัติ

| ประเภทคำขอ | ตัวอย่าง | ผู้อนุมัติขั้นต่ำ | ผู้ดำเนินการ |
|------------|----------|------------------|--------------|
| สิทธิ์พื้นฐาน (Birthright) | อีเมล, SSO พื้นฐาน, อินทราเน็ต | HR ยืนยันสถานภาพ + หัวหน้างาน | IT Access Admin |
| สิทธิ์ธุรกิจทั่วไป | โฟลเดอร์ทีม, แอปแผนก | หัวหน้างาน + System Owner (ถ้ากำหนด) | IT Access Admin |
| สิทธิ์ข้อมูลระดับลับขึ้นไป | ข้อมูลส่วนบุคคล, สัญญา, การเงิน | หัวหน้างาน + Data/System Owner | IT Access Admin |
| สิทธิพิเศษ | Admin, root, cloud owner | หัวหน้างาน + System Owner + ISO/IT Manager | Privileged Access Admin |
| สิทธิ์ผู้รับเหมา/บุคคลภายนอก | VPN ชั่วคราว, โปรเจกต์ | เจ้าของงานภายใน + System Owner | IT Access Admin |
| สิทธิ์ฉุกเฉิน (Break-glass) | กู้ระบบนอกเวลา | IT Manager / On-call lead อนุมัติย้อนหลังได้ภายในกำหนด | On-call Admin |

## 7. เป้าหมายเวลาดำเนินการ (SLA)

| ประเภท | เป้าหมาย |
|--------|----------|
| สิทธิ์พื้นฐานสำหรับพนักงานเข้าใหม่ | ให้พร้อมภายในวันเริ่มงาน หากได้รับคำขอครบก่อนอย่างน้อย 2 วันทำการ |
| สิทธิ์ธุรกิจทั่วไป | ภายใน **2 วันทำการ** หลังอนุมัติครบ |
| สิทธิพิเศษ | ภายใน **1 วันทำการ** หลังอนุมัติครบ หรือตามหน้าต่างเปลี่ยนแปลงที่กำหนด |
| เพิกถอนเมื่อลาออก/หมดสัญญา | **ภายในวันสุดท้ายของการปฏิบัติงาน** หรือทันทีเมื่อแจ้งให้ระงับก่อนกำหนด |
| เพิกถอนฉุกเฉิน (ยึดบัญชี/เหตุรักษาความปลอดภัย) | **ทันที** ตาม PROC-IR-001 |
| ระงับบัญชีผู้รับเหมาเมื่อสิ้นสุดโปรเจกต์ | ภายในวันสิ้นสุดที่ระบุในคำขอ |

## 8. ขั้นตอนการขอสิทธิ์ใหม่ (Access Request / Joiner)

### 8.1 ผู้ขอจัดทำคำขอ

ยื่นผ่านช่องทางที่กำหนด เช่น [ระบุ: ITSM / แบบฟอร์ม / อีเมล] โดยระบุอย่างน้อย

1. ชื่อ-นามสกุล / รหัสพนักงานหรือรหัสผู้รับเหมา
2. หน่วยงาน ตำแหน่ง หัวหน้างาน
3. ประเภทผู้ใช้ (พนักงาน / ชั่วคราว / ผู้รับเหมา)
4. ระบบหรือ role ที่ขอ
5. เหตุผลทางธุรกิจ
6. วันเริ่มใช้ และวันสิ้นสุด (ถ้าเป็นสิทธิ์ชั่วคราว)
7. การเข้าถึงระยะไกลจำเป็นหรือไม่

### 8.2 การอนุมัติ

1. หัวหน้างานตรวจสอบความจำเป็น
2. System/Data Owner อนุมัติเพิ่มเมื่อเข้าเกณฑ์
3. ISO/IT Manager อนุมัติเพิ่มสำหรับสิทธิพิเศษ
4. หากคำขอไม่ครบหรือเกินจำเป็น ให้ตีกลับเพื่อแก้ไข

### 8.3 การดำเนินการโดย IT

1. ตรวจสอบว่ามีบัญชีอยู่แล้วหรือไม่ เพื่อเลี่ยงบัญชีซ้ำ
2. สร้างบัญชีตามมาตรฐานการตั้งชื่อขององค์กร
3. ให้สิทธิ์ตาม role ที่อนุมัติ และเปิด MFA ตาม STD-ITSEC-001
4. ส่งข้อมูลเข้าสู่ระบบแบบปลอดภัย (รหัสชั่วคราว / self-service reset)
5. บันทึกหลักฐานคำขอ การอนุมัติ และสิทธิ์ที่ให้จริง
6. แจ้งผู้ขอและหัวหน้างานเมื่อเสร็จ

### 8.4 สิทธิ์พื้นฐานแนะนำสำหรับผู้เข้าใหม่

- บัญชีตัวตนกลาง (IdP/SSO)
- อีเมลองค์กรและชุดสำนักงานตามสิทธิ์ตำแหน่ง
- สิทธิ์อินทราเน็ต/ระบบ HR บริการตนเองตามที่กำหนด
- MFA บังคับก่อนใช้งานระบบสำคัญ

## 9. ขั้นตอนการเปลี่ยนแปลงสิทธิ์ (Access Change / Mover)

ใช้เมื่อมีการย้ายหน่วยงาน เปลี่ยนตำแหน่ง เพิ่มโปรเจกต์ หรือปรับหน้าที่

1. ผู้ขอหรือ HR แจ้งการเปลี่ยนแปลงผ่านช่องทางคำขอ
2. ระบุสิทธิ์ที่ต้องการ **เพิ่ม** และสิทธิ์ที่ต้อง **ลด/เพิกถอน**
3. หัวหน้างานใหม่และ/หรือเจ้าของระบบอนุมัติ
4. IT ดำเนินการเพิ่มสิทธิ์ใหม่ก่อนหรือคู่กับการลดสิทธิ์เก่าตามแผน เพื่อไม่ให้กระทบงาน โดยต้องไม่ค้างสิทธิ์เก่าเกินจำเป็น
5. สิทธิ์ของหน่วยงานเดิมที่ไม่มีเหตุคงไว้ ต้องเพิกถอนภายใน **3 วันทำการ** หลังวันโยกย้ายมีผล
6. บันทึกการเปลี่ยนแปลงและแจ้งผลให้ผู้เกี่ยวข้องทราบ

> หากผู้ใช้ย้ายไปบทบาทที่ขัดกับหลัก SoD ต้องปรับสิทธิ์ให้เหลือเฉพาะชุดที่ผ่านการประเมินความขัดแย้งแล้ว

---

## 10. ขั้นตอนการเพิกถอนสิทธิ์ (Access Revocation / Leaver)

### 10.1 การพ้นสภาพตามแผน (ลาออก / หมดสัญญา / สิ้นสุดโปรเจกต์)

1. HR หรือเจ้าของงานแจ้ง IT ล่วงหน้าอย่างน้อยตามรอบที่ตกลง และยืนยัน **วัน-เวลาที่มีผล**
2. IT จัดทำ checklist เพิกถอนตามข้อ 10.3
3. ในวันที่มีผล ให้ระงับการเข้าสู่ระบบหลักทันที เช่น SSO อีเมล VPN
4. เพิกถอนสิทธิ์ระบบอื่นที่เกี่ยวข้อง โอนกรรมสิทธิ์ไฟล์/กล่องเมลตามนโยบาย
5. เรียกคืนอุปกรณ์ บัตรผ่าน และโทเคน MFA (ถ้ามี)
6. บันทึกเวลาที่เพิกถอนจริง และปิดคำขอ

### 10.2 การเพิกถอนฉุกเฉิน

ใช้เมื่อมีเหตุทางวินัย การยึดบัญชี ความเสี่ยงต่อข้อมูล หรือคำสั่งผู้บริหาร

1. ผู้มีอำนาจแจ้ง IT/Security ทันที
2. ระงับบัญชีและถอน session โดยไม่ต้องรอวันพ้นสภาพ
3. เก็บรักษาเมล/ไฟล์ตามคำสั่งกฎหมายหรือ HR ห้ามลบทันทีหากเป็นพยานหลักฐาน
4. เปิดเคสตาม PROC-IR-001 หากเกี่ยวข้องกับเหตุความปลอดภัย

### 10.3 Checklist การเพิกถอน

- [ ] ระงับบัญชี IdP / Active Directory / SSO
- [ ] เพิกถอนอีเมล และจัดการ forwarding ตามนโยบาย
- [ ] ตัด VPN / Remote access
- [ ] เพิกถอนสิทธิ์แอปธุรกิจ คลาวด์ ไฟล์แชร์ โค้ดรีโป
- [ ] เพิกถอนสิทธิพิเศษและนำ secret ออกจาก vault ที่เกี่ยวข้อง
- [ ] ถอน session / API token / device trust
- [ ] เรียกคืนอุปกรณ์และ MFA token
- [ ] โอนเจ้าของไฟล์ กลุ่ม และเอกสารสำคัญ
- [ ] บันทึกเวลาเพิกถอนและผู้ดำเนินการ

## 11. สิทธิพิเศษ (Privileged Access)

1. ต้องมีคำขอแยก และระบุเหตุผล ระบบ ระยะเวลา และกิจกรรมที่จะทำ
2. อนุมัติโดยหัวหน้างาน + System Owner + ISO/IT Manager
3. ใช้บัญชีสิทธิพิเศษแยกจากบัญชีปกติ
4. เปิด MFA และเก็บบันทึกการใช้งานตามที่ระบบรองรับ
5. สิทธิ์ถาวรต้องมีจำนวนจำกัดและทบทวนบ่อยกว่าสิทธิ์ทั่วไป
6. สิทธิ์ชั่วคราวควรเป็นค่าเริ่มต้น และหมดอายุอัตโนมัติเมื่อครบกำหนด
7. ห้ามใช้บัญชีสิทธิพิเศษท่องเว็บ อ่านอีเมลทั่วไป หรือทำงานเอกสารประจำวัน

---

## 12. สิทธิ์ผู้รับเหมา บุคคลภายนอก และบัญชีชั่วคราว

1. ต้องมีพนักงานเจ้าของงานภายใน (internal sponsor) ทุกกรณี
2. กำหนดวันเริ่มและวันสิ้นสุดบังคับทุกคำขอ
3. ให้สิทธิ์เฉพาะระบบที่จำเป็นต่อโปรเจกต์
4. เมื่อใกล้หมดอายุ 7 วัน ให้แจเตือน sponsor เพื่อต่ออายุหรือเพิกถอน
5. หากไม่ต่ออายุ ให้ระงับบัญชีอัตโนมัติเมื่อครบกำหนด
6. ห้ามใช้บัญชีกลางของบริษัทผู้รับเหมาแบบไม่ระบุตัวบุคคล เว้นแต่มีข้อยกเว้นและมาตรการชดเชย

---

## 13. บัญชีบริการและสิทธิ์ของระบบ (Service Accounts)

1. ต้องระบุระบบเจ้าของ ผู้รับผิดชอบ และวัตถุประสงค์
2. ห้ามผูกบัญชีบริการกับบุคคลเดียวโดยไม่มีเจ้าของสำรองในระดับทีม
3. ให้สิทธิ์แคบที่สุด และไม่ใช้สำหรับ interactive login ของบุคคล หากไม่จำเป็น
4. เก็บรหัสผ่าน/คีย์ใน secrets vault ตาม STD-ITSEC-001
5. ทบทวนความจำเป็นอย่างน้อยทุก **180 วัน**

---

## 14. การทบทวนสิทธิ์ (Access Review)

| ประเภทสิทธิ์ | ความถี่ขั้นต่ำ | ผู้ทบทวน |
|--------------|----------------|----------|
| สิทธิ์ทั่วไป | ทุก **90 วัน** | หัวหน้างาน / System Owner |
| สิทธิ์ข้อมูลระดับลับขึ้นไป | ทุก **90 วัน** | Data Owner + System Owner |
| สิทธิพิเศษ | ทุก **30–90 วัน** | System Owner + ISO |
| ผู้รับเหมา/ชั่วคราว | ทุก **30 วัน** หรือก่อนหมดอายุ | Internal sponsor |
| บัญชีบริการ | ทุก **180 วัน** | System Owner |

ผลลัพธ์ของการทบทวนต้องเป็นหนึ่งใน: **คงไว้ / ปรับลด / เพิกถอน** และให้ IT ดำเนินการภายใน SLA ของการเปลี่ยนแปลงสิทธิ์

---

## 15. การขอสิทธิ์ฉุกเฉิน (Break-glass)

1. ใช้ได้เฉพาะเมื่อจำเป็นเร่งด่วนต่อการกู้บริการหรือระงับเหตุ และช่องทางปกติใช้ไม่ได้ทันเวลา
2. ผู้ดำเนินการต้องบันทึกเหตุผล เวลา ระบบ และการกระทำทันที
3. แจ้ง IT Manager / ISO โดยเร็ว และขออนุมัติตาม internally ภายใน **1 วันทำการ**
4. หลังเสร็จงานต้องเพิกถอนสิทธิ์ฉุกเฉินและรีเซ็ต credential ที่ใช้
5. มีการสุ่มตรวจการใช้ break-glass เป็นระยะ

## 17. การประสานงานกับ HR และหน่วยงานอื่น

| เหตุการณ์ | ผู้รับผิดชอบแจ้ง | เวลาที่ควรแจ้ง IT |
|-----------|------------------|-------------------|
| พนักงานเข้าใหม่ | HR | อย่างน้อย 2 วันทำการก่อนวันเริ่มงาน |
| โยกย้ายหน่วยงาน | HR / หัวหน้างาน | อย่างน้อย 2 วันทำการก่อนวันมีผล |
| ลาออกตามแผน | HR | เมื่อทราบวันที่มีผล และยืนยันซ้ำก่อนวันสุดท้าย |
| เลิกจ้าง/ระงับฉุกเฉิน | HR + ผู้บริหารที่เกี่ยวข้อง | ทันที |
| สิ้นสุดผู้รับเหมา | เจ้าของงานภายใน | อย่างน้อย 2 วันทำการก่อนวันสิ้นสุด |

## 18. ตัวชี้วัด (KPI)

| ตัวชี้วัด | เป้าหมายแนะนำ |
|----------|----------------|
| % คำขอที่มีการอนุมัติครบก่อนให้สิทธิ์ | 100% ยกเว้น break-glass ที่อนุมัติตามรอบย้อนหลัง |
| เวลาเฉลี่ยในการให้สิทธิ์ทั่วไปหลังอนุมัติ | ภายใน SLA 2 วันทำการ |
| % การเพิกถอนในวันพ้นสภาพ | ≥ 95% และเคสตกค้างต้องมีเหตุผล |
| จำนวนบัญชีชั่วคราวที่หมดอายุแล้วยังใช้งานได้ | 0 |
| % สิทธิพิเศษที่ผ่านการทบทวนตามรอบ | 100% |

## 19. การยกเว้น

1. การขอยกเว้นจากขั้นตอนนี้ต้องระบุเหตุผล ระยะเวลา มาตรการชดเชย และผู้อนุมัติ
2. ต้องบันทึกเป็นลายลักษณ์อักษรและทบทวนอย่างน้อยทุก **90 วัน**
3. การให้สิทธิ์โดยไม่มีคำขอ/การอนุมัติ ถือว่าไม่สอดคล้องกับขั้นตอนนี้ เว้นแต่เป็น break-glass ที่ทำครบตามข้อ 15

---

## 20. การบังคับใช้

การฝ่าฝืนขั้นตอนนี้อาจถูกระงับสิทธิ์ ดำเนินการทางวินัย และ/หรือดำเนินการตามกฎหมาย โดยเฉพาะกรณี

- เปิดสิทธิ์ให้ผู้อื่นโดยไม่ได้รับอำนาจ
- แชร์บัญชีหรือรหัสผ่าน
- ไม่เพิกถอนสิทธิ์เมื่อพ้นสภาพจนเกิดความเสียหาย
- คงสิทธิพิเศษโดยไม่มีเหตุทางธุรกิจ

## 21. เอกสารอ้างอิง

- POL-ITSEC-001 นโยบายการรักษาความปลอดภัยระบบเทคโนโลยีสารสนเทศ
- STD-ITSEC-001 มาตรฐานรหัสผ่านและการพิสูจน์ตัวตน
- STD-ITSEC-002 มาตรฐานการจัดประเภทข้อมูล
- PROC-IR-001 ขั้นตอนการจัดการเหตุการณ์ด้านความปลอดภัย
- ISO/IEC 27001:2022 / ISO/IEC 27002:2022 (Access control)
- พ.ร.บ.คุ้มครองข้อมูลส่วนบุคคล พ.ศ. 2562

## 23. ภาคผนวก ก — สรุป Joiner / Mover / Leaver

| ระยะ | การกระทำหลัก |
|------|----------------|
| **Joiner** | HR แจ้ง → อนุมัติ → สร้างบัญชี → ให้ birthright + สิทธิ์งาน → เปิด MFA |
| **Mover** | แจ้งบทบาทใหม่ → อนุมัติสิทธิ์ใหม่ → เพิ่มสิทธิ์ใหม่และลดสิทธิ์เก่า → ทบทวน SoD |
| **Leaver** | HR/Sponsor แจ้งวันมีผล → ระงับบัญชี → เพิกถอนทุกระบบ → เรียกคืนอุปกรณ์ → บันทึกหลักฐาน |
